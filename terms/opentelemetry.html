OpenTelemetry

first seen 2026-W33 · 3 links · 3 min read

OpenTelemetry, usually shortened to OTel, is a shared specification and set of libraries for recording what a system does: which requests came in, how long each step took, what errors occurred and how services called one another. Because the format is open, the data can be sent to any monitoring vendor, and because auto-instrumentation hooks into popular web frameworks and database drivers, most of the telemetry arrives without developers writing extra code.

For an executive OTel matters because AI changes what needs to be observed. When agents write code and call tools, the question of what the system did and why becomes harder to answer from the source alone, so runtime evidence becomes the primary way of verifying behaviour. Standardising on OpenTelemetry avoids lock-in to a single monitoring vendor and gives teams a common language for the cost, latency and failure data that AI workloads generate. It is a low-cost decision with a long tail of benefit.

Deeper dive

How it works. OpenTelemetry defines a data model for three signals: traces, which record the path of a request across services as a tree of spans; metrics, which record numeric measurements over time; and logs. Language SDKs create this data, and a collector process receives, batches and exports it to whichever backend the team chooses. Auto-instrumentation libraries wrap common frameworks so that HTTP calls, database queries and queue operations produce spans without manual work, and the instrumentation model can be extended so that a wrapper around a model API or a tool call emits spans in the same format.

Why it matters now. The wider Observability discipline is being reshaped by AI-assisted development. When a large share of code is written by agents, reviewers cannot rely on having read every line, so knowing how the code behaves in production becomes the check that matters. Advocates of AI-assisted development argue that auto-instrumentation has made telemetry easier to produce than to skip, which lowers the barrier for teams that previously had none. Small open libraries have appeared that target the OTel format specifically so that lightweight tools and agent calls can be traced without adopting a full vendor stack. The same data feeds Internal benchmarks, since real latency, cost and error distributions are a better yardstick for a model or agent than a public leaderboard.

Trade-offs. Telemetry volume grows with agent activity, and a tool-calling agent can generate orders of magnitude more spans than a request-response service, so sampling and retention policies become cost decisions. Auto-instrumentation gives breadth but not meaning: knowing that a span occurred does not explain why an agent chose that action, so teams still need to capture prompts, tool arguments and decisions as attributes, and that raises data-handling questions when those attributes contain user content. Standards also move slowly, and semantic conventions for AI workloads are still settling.

What to watch. Whether AI-specific semantic conventions land in the standard, whether agent frameworks ship OTel instrumentation by default, and how monitoring vendors differentiate once the data format is shared.

Internal benchmarks

Internal benchmarks are evaluations an organisation writes for its own workloads, testing a model or agent on the tasks it will actually perform rather than on public leaderboards.

Observability

Observability is the practice of instrumenting software so that its behaviour in production can be understood from the telemetry it emits, and it now covers agents as well as services: wide events in place of logs and metrics, traces of hours-long agent runs, and instrumentation added by default.
