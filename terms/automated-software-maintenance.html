Automated software maintenance

first seen 2026-W36 · 10 links · 3 min read

Most engineering effort in an established company goes to keeping existing software working rather than building new features: patching bugs, upgrading libraries, paying down shortcuts taken years ago, and restructuring systems that have outgrown their design. Automated maintenance hands this work to agents that run continuously or on demand, produce changes, and submit them for review. Companies experimenting with it report results better than expected, with the caveat that agent-produced changes still need a person to review before they merge.

The reported scale of change is significant: dependency upgrades that took days now take a couple of hours, and re-architecture that once took years is much faster. For an executive this touches the largest line in the engineering budget. If maintenance can be largely automated, headcount planning, technical-debt decisions and the case for migrations all change. The constraints are review capacity, since someone must still check what the agents did, and the maturity of test coverage, since agents can only verify what tests can catch.

Deeper dive

How it works. A maintenance agent is a coding agent pointed at a class of work rather than a single task. It runs in a Coding harness with access to the repository, the test suite and the build, and takes work from a queue: failing tests, flagged dependencies, lint findings, or a directive such as removing a deprecated pattern across the codebase. For each item it reads the relevant code, makes a change, runs the tests, iterates until they pass, and opens a change request with an explanation. Re-architecture is handled as many coordinated changes: the agent plans the migration, executes it in steps, and keeps the build green throughout. Human review at the merge gate remains, which is the same Code review discipline applied to a much higher volume of changes.

Why it matters now. Two developments made this practical. Coding agents became reliable enough on repository-level tasks that unsupervised runs produce mergeable output more often than not. And the companies building the agents began using them on their own systems, reporting dependency upgrades completed in hours and multi-year re-architecture compressed dramatically. Product companies running the same experiments report outcomes better than they expected. The practice is a component of Agentic engineering, where humans set constraints and review while agents execute, and it overlaps with AI-assisted migrations when the maintenance task is a platform move.

Trade-offs. The output still needs human review, and at high volume review becomes the bottleneck; a team that cannot review at the rate agents produce either slows the agents or lowers its standards. Agents can only verify against tests that exist, so codebases with thin coverage get changes that pass but are wrong. Wide automated changes raise the blast radius of a mistake, and the Software factory pattern of continuous automated change makes incident attribution harder. There is also a knowledge cost: engineers who no longer do maintenance lose the understanding of the system that maintenance built, which matters when something breaks that the agents cannot fix.

What to watch. Whether review tooling, including AI-assisted review, scales to match agent output. Whether organisations report maintenance headcount actually falling, rather than being redeployed. And whether agent-maintained codebases show lower or higher incident rates over time, which is the evidence that would settle whether the practice reduces or relocates risk.

Coding harness

Software factory

A software factory is a production system in which agents run the reproduce, fix, review and verify loop end to end, with humans setting the rules and reviewing a fraction of the output.
