Blast radius

first seen 2026-W17 · 5 links · 3 min read

Blast radius is a way of sizing a risk before deciding how carefully to handle it. Instead of asking whether a change or an automated action might fail, it asks who and what is affected when it does: one user or all of them, a test database or production, a single file or every system an agent has credentials for. The answer sets the level of review, testing and containment that is proportionate.

The idea has moved from deployment practice into agent security. An agent treats whatever text it reads as potential instruction, so a poisoned email or web page can drive actions across every tool the agent can reach. For executives the practical consequence is a budget question: how much sandboxing, credential scoping and human sign-off to buy for each class of agent, and where to stop letting people vibe-code changes whose reach nobody has measured.

Also seen as risk-based review, blast-radius scoping

Deeper dive

How it works. Blast radius is a scoping question applied before an action rather than a post-mortem afterwards. For a code change, the tests are who is affected if it breaks and how far the change can reach: a cosmetic tweak to one page has a small radius, a migration touching shared data or a deployment pipeline has a large one. A badly configured deployment pipeline can take down the whole application, whereas a rollback bounds the damage to one deploy. The scoping then determines the process: a small radius justifies light review and fast iteration, a large one justifies staged rollout, isolation and a second pair of eyes.

Why it matters now. Agents extend the concept because the boundary between data and instruction dissolves. When a model reads a document, a web page or a tool result, that content can steer its next action, and the agent can act on anything it has been given access to. Security analysis describes this as a Turing-complete blast radius: untrusted input becomes executable instruction, so the classical network perimeter no longer bounds the damage. The practical response is AI agent containment, with a trade-off between isolation level and start-up cost that runs from a process sandbox to a full virtual machine. The same measure decides when Vibe coding is acceptable at all: how far can a change the author does not fully understand reach.

Trade-offs. Tight containment is slow and expensive to spin up, and over-scoping every action removes the speed that made agents attractive. Loose scoping shifts the cost to incident response. Reviewers also tend to misjudge radius for changes that look small but touch shared infrastructure, so Code review and Guardrails need explicit rules about what counts as high-reach rather than relying on intuition. Credential scoping is the cheapest lever: an agent that cannot reach a system cannot damage it.

What to watch. Whether Agent security boundaries become standardised enough that blast radius can be computed from an agent's permissions rather than estimated by hand, and whether containment costs fall enough for full isolation to become the default.
