Object storage

first seen 2026-W29 · 4 links · 3 min read

Object storage is a giant labelled locker in the cloud. Files of any size and type go in under a key, are retrieved by that key, and cost a small amount per gigabyte per month with no capacity planning. Unlike a database it does not query the content; unlike a disk it does not belong to any one machine. AWS S3 established the model in 2006 and every cloud now offers an equivalent.

For an executive the term explains two things. First, why the data-infrastructure companies of the last decade, such as Snowflake, Databricks, Neon and Turbopuffer, were able to build on top of the clouds rather than compete with them: they separated storage, which sits cheaply in object stores, from compute, which they sell. Second, how applications built quickly with AI tools should be structured: images, PDFs and uploads go into object storage, and the database holds only a reference. Stuffing files into the database instead is a common and expensive mistake in AI-generated codebases.

Also seen as S3, blob storage, buckets

Deeper dive

How it works. An object store holds immutable blobs under keys in flat namespaces called buckets, with access through an HTTP API. It is designed for durability and scale rather than speed: writes are replicated across facilities, capacity is effectively unlimited, and pricing is per gigabyte stored plus per request and per gigabyte transferred out. It is not a file system and not a database; there are no in-place edits and no queries over content. Its role in an application is to hold anything large or unstructured, with a Database schema that stores only the object's key alongside the structured data.

Why it matters now. The separation of storage from compute is the architectural idea that object storage made cheap. Data warehouses, lakehouses, serverless databases and vector search engines all keep their data in object stores and spin compute up and down against it, which is why they could be built by startups on top of the Hyperscalers rather than requiring their own data centres. The same layer now underpins AI search and retrieval systems. For applications built by Vibe coding, the file-versus-link split is one of the first infrastructure decisions an AI-generated codebase gets wrong, and the guidance in the vault is explicit: big files go in the bucket, the database keeps the link. AI agents that produce artefacts such as reports, images or logs need the same pattern, since their outputs are large and unstructured.

Trade-offs. Object storage is slow for small random reads, which is why compute layers cache aggressively in front of it. Egress charges make moving data between clouds costly, which is a quiet form of lock-in. Access control is coarse and misconfigured public buckets are a recurring source of data leaks. The pattern of storing links rather than files also means the application must handle the case where the object is missing or the link is stale.

What to watch. Object-store-native databases that reduce the need for a separate compute layer, egress pricing competition among clouds and neutral hosts, and agent tooling that defaults to the correct file-versus-database split.
