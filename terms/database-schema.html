Database schema

first seen 2026-W35 · 5 links · 3 min read

A database schema is the rulebook that says what data an application stores and how it is shaped. Application code is written against it, so a change to the schema is a change to the contract that every part of the system relies on. Adding a column is usually safe; renaming or removing one can break code that still expects the old shape.

It matters now because AI coding tools generate application code quickly and cheaply, which shifts the question of what humans should still review. One position from a startup founder is that the schema is the single artefact worth human review, since it is the rigid part of the system and the hardest to undo. A counter-position holds that this fits a startup seeking product-market fit, while an established business should guard its business logic with tests instead. For an executive the point is where to place scarce review attention and how to prevent a fast-moving AI-written codebase from corrupting the data underneath it.

Also seen as schema, schema changes

Deeper dive

How it works. The schema defines tables, columns, types, constraints and the relationships between them, and the application's queries assume that shape. Schema changes are applied through migrations, and the dangerous moment is the deploy window in which old code is still running against a new schema or new code against an old one. The standard discipline is to make changes additive: add the new column, deploy code that writes to both, backfill, switch reads, and only then drop the old column. Skipping steps is one of the classic failure points of a vibe-coded application, and the blast radius depends on how defensively the surrounding code was written.

Why it matters now. Vibe coding and agentic tools produce application logic faster than teams can read it, so review effort has to be rationed. One founder's answer is to treat the schema as the one rigid artefact and route every schema change through a human, letting the model own everything above it. The counter-argument accepts that for a startup without product-market fit, where the schema will be rewritten anyway, but holds that an established business has more value at risk in its business logic and should protect that with tests rather than concentrate review on tables. Both positions agree that AI code review handles the volume and humans handle the contracts.

Trade-offs. Concentrating review on the schema is cheap and catches the irreversible errors, but it leaves logic errors to tests that may not exist. Making all changes additive avoids the deploy window at the cost of accumulating dead columns and a second cleanup migration. Text-to-SQL and query-generation systems raise the bar from the other side: schema-compliant output is a precondition for such systems, not a quality measure, and recent work selects training data by schema and table coverage to make sure generated queries exercise the whole structure.

What to watch. Whether agent tooling starts to enforce the additive-change rule automatically, whether AI-assisted migrations become reliable enough to move schema review back to machines, and how teams split the Code review budget between structure and logic as AI-written code becomes the majority of the codebase.
