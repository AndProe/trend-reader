Agent harness

first seen 2026-W30 · needed by 2 · 12 links · 3 min read

An agent is a model plus a harness. The model produces text and decisions; the harness turns those into actions by giving the model tools, a sandbox or a real system to act on, a loop that feeds results back, and policies that block or require approval for certain steps. The same word is also used for the scaffolding that makes an evaluation realistic and for the loop that trains an agent.

The business point is that the harness is where products differ. One published result had a harness change move a general-reasoning score by 37 points, more than the model contributed, and in several papers the harness rather than the model is what gets optimised, sometimes automatically. Two consequences follow. Model choice is less decisive than it looks, and switching models is easier if the harness is model-agnostic. And the harness is where a company's own margin sits: specialised harnesses widen the gap between a generic assistant and a product that reliably operates a specific system.

Also seen as multi-agent harness, deployment-imitating harness, harness

Deeper dive

How it works. A harness has four parts. Tools: the functions, APIs and interfaces the model may invoke, from a shell and a file system to a browser or a hardware device. Permissions and policies: what the model may do without asking, what needs approval and what is blocked, applied by the harness at specific states so the model and prompt stay untouched. The loop: the control flow that reads the model's output, executes it, returns observations and decides whether to continue, retry, spawn parallel agents or stop. And the environment: a sandbox, a container with local tools, or a live system. Everything a product manager builds so an agent can safely and completely operate a system on a user's behalf lives here, which is why Harness engineering has become a named discipline distinct from prompt engineering and model training.

Why it matters now. A general-reasoning benchmark result swung by 37 points on harness changes alone. Research papers now treat the harness as the object of automated search, evolving tool sets and loop structures rather than weights. When environments are used as a training curriculum, the harness gains importance as models improve. Vendors have begun shipping execution evidence with weights so users can reproduce the harness the model was tuned in. And Coding harness products, from terminal agents to computer-use systems, are where most enterprise agent spend currently lands. The counter-view is that as models absorb more of the loop, harnesses and models converge, and some who built one now qualify the claim that harness integration is the main differentiator.

Trade-offs. A tightly integrated harness extracts more from a specific model but ties a product to it; a Model-agnostic architecture preserves switching freedom at some cost in performance. Benchmarks that let each lab choose its own harness measure a system, not a model, and a model trained mostly inside one harness performs best there; the call for auditable open-source computer-use harnesses follows from this. The same tooling is dual-use: harnesses built for productive coding agents also appear as attacker tooling in misuse reports. Guardrails inside the harness can be bypassed by anything that reaches the model with a tool the harness does not know about.

What to watch. Whether harness design becomes standardised through protocols that make harnesses interchangeable, or stays proprietary as the product moat. Whether automated harness optimisation reaches production. And whether Reinforcement learning environments and harnesses merge, so that the system an agent is trained in and the one it is deployed in become the same artefact.

Harness engineering

Harness engineering is the practice of designing the tooling, prompts, permissions and feedback loops around a model so that the model performs reliably on real tasks.

Model-agnostic architecture

Model-agnostic architecture is the design of a product or platform so that any model backend can be swapped in without rebuilding the product.

Reinforcement learning environments

Reinforcement learning environments are synthesised, verifiable task settings, such as sandboxed code repositories, simulated devices or games, in which an agent acts, receives a graded reward and is trained on the result.

Benchmarks

Benchmarks are standardised tests that score AI models on fixed tasks, from vendor-reported tables at each release to third-party leaderboards and research suites.

ARC-AGI-3
