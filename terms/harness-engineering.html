Harness engineering

first seen 2026-W30 · needed by 2 · 9 links · 3 min read

A harness is everything wrapped around a model call: the system prompt, the tools it can invoke, the sandbox it runs in, how results are checked, when a human is asked, and how failures are retried. Harness engineering is the discipline of building that layer well. It sits on an abstraction ladder that runs from prompting a model, to designing its harness, to engineering the loops that run it, to factories that run many loops. Empirical studies now treat harness design as the unit of improvement: the same model scores very differently depending on the harness.

For an executive, this is where differentiation moved once frontier models converged. Two companies with the same model can get different results, and the difference is harness quality. It is also where the margin sits: harness products charge above the token price. The decision it touches is whether to build harness capability in-house, buy it from a vendor, or accept a lab's own harness and the lock-in that comes with it.

Also seen as harness design

Deeper dive

What it covers. A harness is the runtime environment of a model: the instructions it receives, the tools exposed to it, the permissions that gate those tools, the sandbox it operates in, the verification applied to its outputs, and the failure handling that decides whether to retry, escalate or stop. A Coding harness adds repository access, test runners and version control; a general Agent harness adds browsers, files and messaging. Harness engineering is designing these deliberately, with the same rigour applied to the model itself. On the abstraction ladder, it sits above prompting and below Loop engineering, which arranges harness runs into iterating processes, and the factory patterns of Agentic engineering that run many loops at once.

Why it is the unit of improvement. Benchmarks such as SWE-bench Verified and Terminal-Bench report large spreads for the same model under different harnesses, and an empirical study of coding-agent harness design finds the choices about tools, context management and verification are decisive. Failure-informed approaches go further: they log where an agent's runs go wrong and engineer the runtime around those failure states, denying or checking actions at the points that precede them. Because a harness can be changed in hours while a model takes months, most of the improvement a team can control lives in the harness.

Trade-offs. A richer harness improves reliability but adds latency, token cost and surface area for bugs and prompt injection. Harnesses are also model-specific in practice; the tuning that works for one model degrades on another, so switching models means reworking the harness. Vendors' harnesses are convenient and opaque, which is the lock-in question. And harness quality is hard to measure outside benchmarks, so teams tend to over-fit to public suites.

What to watch. Whether harness design converges on shared standards or stays proprietary. Whether the labs absorb harness features into the model, reducing the layer's value. And whether harness margin holds as labs ship their own agent products.

Coding harness

A coding harness is the software layer wrapped around a language model that turns it into a working coding agent: the loop that manages context, calls tools, runs tests and decides what to do next.

Loop engineering

Loop engineering is the practice of designing systems in which an AI agent prompts, executes, tests and verifies its own work repeatedly until a stopping condition is met, so that the human designs the loop rather than writing the code inside it.

needed by 1 · 8 linksconcept

Agentic engineering

Agentic engineering is the discipline of building software with coding agents deliberately: engineers specify, constrain, verify and review while agents write most or all of the code, in contrast to unstructured vibe coding.

needed by 1 · 9 linkstechnique

Agent harness

An agent harness is everything around the model that lets it operate a system: the tools it can call, the permissions it holds, the loop that decides when to act again, the environment it runs in and the checks applied to its outputs.

SWE-bench Verified

SWE-bench Verified is the human-validated subset of SWE-bench, a benchmark in which a coding agent must resolve real GitHub issues from open-source repositories and pass the hidden tests.
