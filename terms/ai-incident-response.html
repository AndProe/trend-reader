AI incident response

first seen 2026-W37 · 8 links · 3 min read

AI incident response puts an agent alongside the on-call engineer rather than in place of them. When an alert fires, the agent pulls logs, traces, recent deployments and similar past incidents into one summary, proposes mitigations, and in more advanced setups turns a production alert into a proposed code fix. The engineer decides. OpenAI's internal tooling is the reference case: an incident agent that gathers context and proposes without executing, and a pipeline that converts performance alerts into candidate fixes.

It matters because incident response is where the cost of agent-driven engineering surfaces. More code shipped by agents means more incidents, and the agents themselves add load to the infrastructure that serves them. Keeping a human in the approval seat limits the damage from a wrong mitigation but raises a skills question: an engineer who only approves proposals gradually loses the ability to diagnose from scratch. For an executive the decision is how far to let agents act in production and how to keep the on-call skill base alive.

Also seen as agentic incident response, incident agents

Deeper dive

How it works. The incident agent sits on top of Observability: it needs logs, metrics, traces and deployment history in a queryable form, which is why organisations without solid telemetry cannot use one. On an alert it assembles a context pack, correlates the alert with recent changes, searches past incidents for matches, and proposes a ranked set of mitigations such as a rollback, a feature-flag change or a scaling action. A separate pipeline can take a performance alert, locate the regressing code and open a proposed fix that goes through the normal review path, where AI code review and tests act as the gate. In the reference deployments the agent never executes; a person approves each step, and on-call duty stays with people.

Why it matters now. This is part of the Software factory model in which agents write most code and humans supervise a pipeline. The incident path is the pipeline's feedback loop, and it is also where agent load becomes visible in infrastructure, since fleets of agents running tools contribute to the CPU shortages that some organisations reported in 2026. As Automated software maintenance grows, the fraction of incidents caused by agent-written changes and resolved by agent-proposed fixes rises, and the human role narrows to judgement under time pressure.

Trade-offs. Propose-but-not-execute keeps control but caps the speed gain; a mitigation that waits for a human at 3 a.m. is as slow as before. Full automation removes the wait but makes a wrong mitigation an incident of its own, which is the Agent reliability problem in its sharpest form. The skills question is the long-term cost: diagnostic ability atrophies when the agent always goes first.

What to watch. Whether any large operator lets agents execute low-risk mitigations unattended, how incident rates move as agent-written code dominates, and whether on-call rotations change to keep diagnostic skills current.

Observability

Automated software maintenance

Automated software maintenance is the use of coding agents to do the upkeep of a codebase, such as fixing bugs, removing technical debt, upgrading dependencies and re-architecting, without a human driving each task.

Agent reliability

Agent reliability is whether an agent completes a given workflow acceptably often enough to be trusted with it, measured as a target such as success on nearly every run under a defined oversight policy and cost, rather than as a best-case capability score.

Software factory

A software factory is a production system in which agents run the reproduce, fix, review and verify loop end to end, with humans setting the rules and reviewing a fraction of the output.
