Loop engineering

first seen 2026-W34 · needed by 1 · 8 links · 3 min read

Loop engineering means building a cycle rather than a one-shot request. An agent is given a goal, a way to act, a way to check its result and a rule for when to stop; it then runs on its own, fixing what the check rejects. Examples include an implementer loop that works through a ticket queue, a daily loop that proposes architecture improvements, and research methods that evolve an agent's training environment in the same iterative way.

For an executive the shift is in what engineers are paid to do. When the loop is well designed, the code inside it is produced and corrected by the agent, so the scarce skill becomes specifying goals, tests and guardrails. That changes hiring profiles, tooling budgets and the definition of a productive engineer. It also introduces a cost that does not exist with a person: a loop with a weak check can run indefinitely and confidently produce the wrong thing, so the quality of the verification step is the quality of the output.

Also seen as agentic loops, autonomous loops

Deeper dive

How it works. A loop has four parts: a prompt or goal, an action step in which the agent writes code or runs tools, a verification step such as tests, type checks, a reviewer agent or production telemetry, and a controller that decides whether to iterate, escalate or stop. The simplest form re-runs the same prompt against a task until the tests pass. More elaborate forms chain loops: one agent implements tickets while another reviews, and a scheduled loop scans the codebase for improvements. Recent research makes the controller explicit by compiling agent skills into finite state machines, so the control flow is a specified artifact rather than something the model infers each turn. The same pattern appears as a research method in work that evolves terminal-agent environments through repeated generate-test-refine cycles.

Why it matters now. Harness engineering provides the scaffolding, and loop engineering is what runs inside it. The observation that current engineering work is about shaping the loop rather than the code within it marks a change in the division of labour: engineers specify, agents produce, and Verification loops carry the burden of correctness. At scale this becomes the Software factory, where many loops run concurrently over a backlog. It also reframes some model limitations: planning fatigue in long sessions is reported as a property of the loop design rather than of the model, which means it can be fixed by restructuring rather than waiting for a better model.

Trade-offs. A loop is only as good as its stopping criterion. Weak tests let the agent converge on something that passes without being right, and a loop with no budget can consume tokens without limit. Loops also hide work: when a person no longer reads the code inside the loop, review must move to the loop's outputs and metrics, which is why the same discussions pair loops with production observability and reviewer agents. Well-designed Reinforcement learning environments and well-designed engineering loops share this dependency on a reliable reward signal.

What to watch. Standard loop templates in agent tooling, controllers that expose the loop's state for audit, and whether teams measure loop success rates as a first-class engineering metric.

Harness engineering

Harness engineering is the practice of designing the tooling, prompts, permissions and feedback loops around a model so that the model performs reliably on real tasks.

Software factory

A software factory is a production system in which agents run the reproduce, fix, review and verify loop end to end, with humans setting the rules and reviewing a fraction of the output.

Verification loops

Verification loops are pipelines in which an agent's change is automatically tested and, if it fails, retried until it passes a defined check.

Reinforcement learning environments

Reinforcement learning environments are synthesised, verifiable task settings, such as sandboxed code repositories, simulated devices or games, in which an agent acts, receives a graded reward and is trained on the result.

IDE decline

IDE decline is the observation that time engineers spend in a code editor falls as work moves into agent harnesses, where the agent types and the engineer directs and reviews.
