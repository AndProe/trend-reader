AI code review

first seen 2026-W23 · 8 links · 3 min read

AI code review puts a model in the reviewer's seat. It reads a diff, checks it against coding standards and security rules, flags tautological tests and questionable logic, and either comments or blocks the merge. The current practice runs several reviewers per change, sometimes different models and sometimes agents specialised by domain, after an implementer agent has produced the code.

It matters because the alternative is no review at all. When one engineer receives fifty AI-written changes in a batch, human reviewers miss things, and some teams have simply stopped reading agent-written code for prototypes. Security findings from review models now block merges in several organisations, and the reviewer agent is described as one of the three mechanisms that keep an agent-heavy engineering system resilient. For an executive the decision is whether review capacity, human or automated, scales with the generation capacity being bought, because a widening gap between the two is where incidents come from.

Also seen as automated code review, diff review

Deeper dive

How it works. A review agent receives the diff, the surrounding code and the team's standards, then produces findings ranked by severity. Stronger setups chain reviewers: an implementer agent writes the change, a review agent enforces conventions and catches tests that assert nothing, and further specialists check security, data-model changes and performance. Multi-model review runs the same diff through several models to reduce blind spots. The findings feed back into the implementer loop, which is the basis of Verification loops in an agentic pipeline, and the same judgement-by-model pattern underlies LLM-as-judge evaluation more broadly.

Why it matters now. Review has become the bottleneck of software production. Agent-heavy teams generate more changes than any human can read with attention, so the human role shifts from reading every line to reviewing the output of vendor and in-house review bots, or to sampling. Review models are now benchmarked as superhuman on defect finding, and security findings block merges. Inside the Software factory model of engineering the reviewer agent is a load-bearing component alongside tests and observability rather than an add-on. The diff-review habit is even being borrowed back into prose work, where editors review model changes as diffs rather than editing directly.

Trade-offs. Automated review inherits the model's blind spots and can approve plausible-looking code that is wrong in a way no reviewer model was trained to see. It adds latency and token cost to every change. Standards it enforces must be written down, which many teams have never done. And a review layer that is trusted too completely can hide the fact that nobody understands the code base any more; see Code review for the human practice being displaced and TDD for the complementary discipline of tests written before code.

What to watch. Whether review agents gain authority to block merges by default across large organisations, whether audit and compliance regimes accept model review as evidence, and whether the gap between code generated and code read keeps growing.
