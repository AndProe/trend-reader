Rust

first seen 2026-W33 · 2 links · 3 min read

Rust is a programming language designed to run as fast as C and C++ while preventing the memory errors that cause most security vulnerabilities in those languages. Its compiler refuses code that could corrupt memory, which makes it slower to write but removes a whole category of production failures. It has grown from an enthusiast language to a default choice for infrastructure, command-line tools and performance-sensitive services.

For an executive the relevant signals are where it is being adopted and why. Proprietary trading firms use it for research tooling and orchestration rather than to replace their C++ trading cores. A leading coding agent chose it for correctness, efficiency and a hard boundary between the agent and the product around it. The counter-signal is the blog-post genre announcing a rewrite in Rust, which one performance specialist reads as evidence that the original architecture failed rather than that the language succeeded. The budget question is engineering time: Rust costs more to write and less to operate.

Deeper dive

How it works. Rust enforces an ownership model: every value has one owner, references are checked for lifetime and aliasing at compile time, and the compiler rejects programs where a pointer could outlive its data or two writers could race. The result is memory safety and thread safety without a runtime garbage collector, so binaries are small, start instantly and run at native speed. The cost is a steeper learning curve and longer compile times, and the ownership rules make some designs awkward, which is why teams often keep C++ for legacy cores and adopt Rust for new components at the edges.

Why it matters now. Two adoption patterns stand out in the evidence. At quantitative trading firms Rust is growing in research tooling and orchestration, the layers where correctness and developer productivity matter, while the latency-critical Quantitative trading engines stay in C++. At a frontier lab the coding agent's core was written in Rust for correctness, efficiency and a hard boundary between the agent and the product, a choice that reflects how agent harnesses have become performance-sensitive infrastructure rather than scripts. Both point to the same logic: Rust where bugs are expensive and the code is new.

Trade-offs. The rewrite-in-Rust announcement is a recognisable genre, and the case against it is that a rewrite rarely fixes what a language change alone can fix. Read that way, a dramatic speed-up after a rewrite is evidence that the original system's architecture was wrong, and the same gain might have been available in the original language with better design, which is the core argument of the Software performance discussion. Rust also raises the cost of iteration, which matters for AI-generated code: agents produce more code faster, and a compiler that rejects unsound code is a useful check on that output but slows the loop.

What to watch. Whether coding agents make Rust's learning curve irrelevant by writing the ownership-correct code themselves, and whether trading firms and labs extend it from tooling into their latency-critical cores.
