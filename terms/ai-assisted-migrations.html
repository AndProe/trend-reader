AI-assisted migrations

first seen 2026-W34 · 11 links · 3 min read

AI-assisted migrations apply coding agents to the least glamorous work in software: moving a code base from one framework, language version or test library to another. Such migrations were deferred for years because they consumed senior engineers on repetitive changes across thousands of files. Case studies from Asana, Airbnb, Uber, Bun and Sentry describe agents doing the bulk of that work, with pipelines that attempt a change, run the tests, and retry until it passes.

The economics are the point. A migration that would have cost a team a year can be scoped in weeks, which means debt that was never going to be paid now can be, and platform teams can standardise across an organisation. The caution is specific to data: AI-generated database migrations should be treated with suspicion and tested on staging, because a wrong schema change is not undone by re-running the tests. For an executive the decision is which deferred migrations become worth doing, and how to keep verification rigorous once the mechanical work is cheap.

Also seen as migrations with AI, LLM-aided migration, test framework migration

Deeper dive

How it works. A migration decomposes into many small, similar changes, which suits agents. The pipeline hands each unit to an agent inside a Coding harness with the target pattern, examples of completed conversions and the test suite; the agent makes the change, runs the tests, reads failures and retries. The Verification loops are what make this work at scale, since the tests define success and the agent need not be right first time. Human engineers write the conversion guide, handle the units that fail repeatedly and review samples. The reported case studies span test-framework migrations, language-version upgrades, runtime swaps such as moving to Bun, and cross-service consistency changes.

Why it matters now. The cost of mechanical change has fallen faster than the cost of judgement, which favours exactly this work. Organisations adopting the Software factory model treat migrations as a continuous background process rather than a project, part of the shift to Automated software maintenance. Lowering migration cost also changes technology choices: a team can adopt a new framework knowing the next move will be cheap, and platform teams can enforce standards they could previously only recommend.

Trade-offs. Tests define success, so a migration is only as safe as the test suite, and agents will make tests pass in ways that miss the intent. Data migrations are the sharp case: a Database schema change generated by a model and applied to production without a staging run can destroy data, and no retry loop recovers that. Wide automated changes also strain review capacity and the source-control systems that carry them. The same tooling in the hands of non-engineers through Vibe coding produces migrations nobody understands.

What to watch. Whether migration case studies report post-migration defect rates, whether staging and rollback discipline holds as migrations become routine, and whether frameworks start designing for agent-driven upgrades.

Coding harness

A coding harness is the software layer wrapped around a language model that turns it into a working coding agent: the loop that manages context, calls tools, runs tests and decides what to do next.

Verification loops

Verification loops are pipelines in which an agent's change is automatically tested and, if it fails, retried until it passes a defined check.

Software factory

A software factory is a production system in which agents run the reproduce, fix, review and verify loop end to end, with humans setting the rules and reviewing a fraction of the output.
