Software performance

first seen 2026-W35 · 6 links · 3 min read

Performance engineering is the work of making software fast. Two approaches exist. Hotspot optimisation profiles a running system, finds the few functions consuming most of the time and fixes them. Architectural performance designs the system from the start so that data flows efficiently. The argument gaining ground is that hotspot fixes only work when the architecture allowed for speed in the first place; a system built without regard for performance cannot be profiled into being fast.

For an executive the relevance is cost at scale. In AI infrastructure a small inefficiency is amplified across every machine in a cluster, which is the amplification cost pushing labs off Python for performance-critical paths and towards languages such as Rust. Performance is also part of the trade-off with development speed: fast-to-write languages and frameworks buy iteration at the expense of runtime cost. The budget question is when that trade stops paying, which for most companies arrives when the compute bill exceeds the engineering bill.

Also seen as performance engineering, hotspot optimization, Python performance

Deeper dive

How it works. Performance work happens at three levels. At the algorithmic level the choice of data structures and complexity classes sets the ceiling. At the architectural level the arrangement of data in memory, the number of layers between a request and the work, and the amount of copying and allocation decide how close a system can get to that ceiling. At the hotspot level a profiler finds where time is actually spent and the engineer fixes those places. The case made by performance specialists is that the third level is only recoverable when the second was done well: profile-and-fix works if the architecture was designed for it, and the rewrite-in-Rust genre is read as evidence that it was not, with the language change getting credit that belongs to the redesign. Rust and the languages used in Quantitative trading are where the discipline has been kept alive.

Why it matters now. Performance has been treated as under-valued and is rising in importance. Two forces drive that. AI infrastructure amplifies inefficiency: an interpreter overhead that is invisible on one machine is a material cost across a training or serving fleet, which is why labs move performance-critical code out of Python. And AI-generated code makes the trade-off explicit, since agents can produce large volumes of working but slow code, and the Prompt-to-game and real-time-application cases show where that becomes a user-visible problem. The speed half of the language trade-off, once a niche concern, is now part of choosing a stack.

Trade-offs. Optimising early costs development time and can lock in designs before requirements are known; optimising late may be impossible if the architecture forbids it. Performance-oriented languages slow iteration and narrow the hiring pool. Test-driven practices such as TDD protect correctness during optimisation but do not measure speed, so performance needs its own benchmarks. The discipline is also a matter of Engineering culture: teams that measure latency and cost per request keep it, teams that measure only features lose it.

What to watch. Whether coding agents learn to write performance-aware code or merely more code, and whether the compute bill drives a broader return of performance engineering outside labs and trading firms.
