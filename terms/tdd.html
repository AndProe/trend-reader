TDD

first seen 2026-W35 · 9 links · 3 min read

Test-driven development (TDD) reverses the usual order of work: the engineer writes a small automated test that fails, then writes just enough code to make it pass, then tidies up and repeats. The test is the specification, and a green test suite is the evidence that the code does what was asked.

The practice is decades old, but it has found a new role as an instruction set for coding agents. Skill libraries now ship TDD as a markdown workflow an agent follows, turning it into a feedback loop that catches errors before a human reviews them. For an executive, the relevant question is not whether engineers write tests first, but whether the team's agent workflows carry an explicit verification step; without it, throughput gains from AI-written code arrive with quality risk attached. TDD is one of the cheapest such steps, though it is contested as a universal default, particularly where performance-sensitive design decisions must precede any test.

Also seen as test-driven development, test-first development

Deeper dive

How it works. The loop is red, green, refactor: write a test that fails because the feature does not exist, write the minimal code that passes it, then clean the code while the test guards against regressions. The discipline forces small increments and an executable definition of done. When a coding agent runs the loop, the failing test becomes the prompt's ground truth; the agent iterates until the suite passes rather than declaring success on its own judgement.

Why it matters now. Agent workflows need machine-checkable stopping conditions, and TDD supplies one that already exists in most codebases. Packaged as a skill in a Skill library, it is one of several markdown workflows an agent can be told to follow, alongside code review and debugging routines. Practitioners increasingly recast it as a feedback loop rather than a memory aid: the point is not documentation but continuous validation of AI output. This is why it sits inside the broader family of Verification loops and pairs with Self-verification by the model.

Trade-offs. TDD is established but contested. Performance-minded engineers reject 'driven' as a default, arguing that data layout and algorithm choice should be designed deliberately rather than emerge from the smallest passing change; tests then verify a design rather than produce it. Tests also encode the author's assumptions, so an agent that writes both test and code can satisfy its own weak test. Some teams therefore ask the agent for proof that a change would fail without it, rather than a full test-first regime.

What to watch. Whether TDD skills become a standard component of coding harnesses, how teams separate test construction from implementation to keep the loop honest, and whether AI code review absorbs the verification role that tests-first once played. The contrast with Vibe coding is the practical one: the same agent, with or without a verification target.

Skill library

A skill library is a store of reusable, named procedures that an agent can load and apply, whether taught by demonstration, written by hand as instructions, derived from failure diagnoses or compiled into executable artefacts.

Software performance

Software performance is the discipline of making code run fast and use resources efficiently, through architecture that permits speed and through profiling and fixing hotspots.

Self-verification

Self-verification is an AI system checking its own work before declaring it done, either inside the model's reasoning or through a harness that runs tests, reads telemetry, inspects screenshots and selects among candidate answers.

AI code review

The use of language models to review code changes, from a single bot that comments on a pull request to multiple specialist agents that gate merges.

Code review

Code review is the human inspection of a code change before it is merged, historically the main quality gate in software teams.
