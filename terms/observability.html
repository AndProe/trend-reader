Observability

first seen 2026-W33 · needed by 2 · 8 links · 3 min read

Observability means being able to ask a running system what happened and get an answer. Traditional practice collected logs, metrics and traces separately; the current approach records one wide event per unit of work, rich with context, and derives everything else from it. For agents, the unit of work is a run that may last hours and spawn sub-runs, so the telemetry becomes traces of traces, and auto-instrumentation makes capturing it easier than not capturing it.

For an executive observability is the answer to a governance question: when an agent acted on the company's behalf, how do we know what it did and why. It is listed alongside tests and reviewer agents as one of three independent checks on agent output, and the recommended first step for any organisation deploying agents is to measure success and failure rates per agent. The budget touches tooling, storage for retained run history and the engineering discipline to instrument before scaling, and the risk of skipping it is running autonomous systems blind.

Also seen as tracing, spans and traces, wide events, meta-traces

Deeper dive

How it works. Modern observability captures a wide event for each request or task: a single structured record carrying every attribute that might later matter, from user and version to timing and outcome. Metrics and logs become queries over these events rather than separate pipelines. For agents the event is a span in a trace, and a long agent run becomes a tree of spans across model calls, tool calls and sub-agents; tooling now offers timelines that show traces of traces for hours-long workflows. OpenTelemetry is the common instrumentation standard, and libraries exist to wrap an agent framework so every call is validated, seeded and traced with minimal code. Auto-instrumentation has reached the point where adding telemetry is easier than leaving it out.

Why it matters now. Agents make observability a control rather than a diagnostic. Production telemetry is one of three independent checks on agent work, with tests and a reviewer agent as the other two, and the first step recommended to an organisation adopting agents is to record success and failure rates for every one. Inside a software factory, deploy agents build per-change dashboards and performance agents read production signals to decide what to fix. Research on production benchmarking shows that calibrating evaluations of an evolving agent depends on retained run history, with a one-day window tolerated by the deployed method. Even pipeline frameworks for scientific data now describe filtering ledgers and cross-stage anomaly detection as observability claims.

Trade-offs. Wide events are expensive to store at agent volumes, and long traces are hard to read without tooling. Telemetry shows what happened, not whether it was right; that still needs Verification loops and Internal benchmarks. Distinguishing build-phase failures from runtime failures is a first diagnostic split that inexperienced teams miss. And observability of a multi-agent swarm reveals activity but not causation; attributing which agent drove an outcome is an interpretability problem, not a telemetry one. For AI incident response, the value depends on retention: an incident found weeks later needs traces that were kept.

What to watch. Agent-native tracing standards, retention policies that match the horizon of agent runs, and whether success-rate dashboards per agent become a reported operational metric.

OpenTelemetry

OpenTelemetry is the open, vendor-neutral standard for collecting traces, metrics and logs from software, with libraries that instrument common frameworks automatically.

Internal benchmarks

Internal benchmarks are evaluations an organisation writes for its own workloads, testing a model or agent on the tasks it will actually perform rather than on public leaderboards.

needed by 1 · 13 linkstechnique

Verification loops

Verification loops are pipelines in which an agent's change is automatically tested and, if it fails, retried until it passes a defined check.

needed by 3 · 14 linkstechnique

Self-verification

Self-verification is an AI system checking its own work before declaring it done, either inside the model's reasoning or through a harness that runs tests, reads telemetry, inspects screenshots and selects among candidate answers.

6 linkstechnique

AI incident response

The use of agents in the on-call path: gathering context when an alert fires, proposing mitigations and, in some setups, drafting the fix.
